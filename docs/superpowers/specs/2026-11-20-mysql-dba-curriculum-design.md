# MySQL DBA 学習トラック 設計

- 日付: 2026-11-20
- 状態: 承認待ち
- 置き場所: `mysql-dba/`（このリポジトリの中に、既存の学習計画とは独立して作る）

## 1. なぜ作るか

業務で Aurora MySQL を使っていて、DBA に近いポジションの仕事をしている。ただ、MySQL の中の仕組みはまだよく分かっていない。DB に詳しい同僚とアーキテクチャやパラメータの話をするときに出てくるキーワード（binlog がその代表）が分からないので、そこを強化したい。

本人の言葉では「DBA を名乗れるほどにはまだ詳しくないので、MySQL の全体像を分かりやすく深く解説してもらうのが良い。その中でも binlog は、他サービスとのデータ連携でも使うので、さらに少し深く」。

なので、このトラックでやるのは次の2つ。

- MySQL の**全体像の地図**を作る。どの部品が何をしていて、どのパラメータがどこに効くかを、つながりとして理解する
- 地図の中でも **binlog** は深めにやる。レプリケーションと、他サービスとのデータ連携（CDC）まで

読むだけで終わらせず、Docker で実際に動かして「解説に書いてあることが本当に起きる」のを自分の目で確かめる。

### 想定する読み手

このリポジトリの持ち主本人。

- **前提にしてよいこと:**
  - SQL は書ける（`sql/` で自己結合、集合演算、粒度の問題を解いている）
  - DWH 側の仕組み（Snowflake のマイクロパーティション、Spark の実行計画や shuffle、列指向）を学んでいる
  - 業務で Aurora MySQL を使っている
- **知らない前提で書くこと:** MySQL の中の仕組み

なので、SQL の基礎や「インデックスとは何か」の説明は要らない。その代わり、中の仕組みの用語（ページ、LSN、fsync、スナップショット、purge など）は、最初に出てきたときに丁寧に説明する。DWH の知識と比べると分かりやすくなるところは比べる。たとえば、行指向のページと列指向のファイル、MVCC と Snowflake の Time Travel、binlog と Delta Lake のトランザクションログ。

## 2. ゴール / やらないこと / 失敗とみなすこと

### ゴール

- 1回の `UPDATE` が、接続 → SQL 層 → InnoDB（バッファプール、undo、redo）→ binlog → コミット → レプリカ・CDC の利用者に届くまでを、図を描きながら自分の言葉で説明できる
- 主なパラメータ（`innodb_buffer_pool_size`、`innodb_flush_log_at_trx_commit`、`sync_binlog`、`binlog_format`、`binlog_row_image`、`transaction_isolation` など）について、「何を決めるか」「変えると何が起きるか」を、自分で観察した結果を使って説明できる
- binlog について、次のことを説明できる
  - 何が記録されているか
  - redo ログとの違い
  - コミットのときに redo と binlog をどうやってそろえているか
  - レプリケーションと CDC がどう読んでいるか
  - CDC で何が必要で、何をすると壊れるか
- それぞれの仕組みが Aurora MySQL ではどうなっているか（同じか、置き換わっているか）を言える。同僚との会話を業務の Aurora に結び付けられる
- 同僚との会話に出てくるキーワードを聞いて、地図のどこの話かが分かる

### やらないこと

- バックアップとリストア、フェイルオーバーと高可用性の運用（Aurora がやってくれるので）
- インストール、OS のチューニング
- EXPLAIN とインデックス設計によるクエリのチューニング（`rdbms/` で扱う予定なので重複させない。インデックスの「構造」は第2部で扱う）
- 資格試験の対策
- AWS 上でしかできない操作の演習（Aurora については注記で扱う）

### 失敗とみなすこと（動いても目的を外しているもの）

- 「なぜそうなっているか」がない、パラメータや用語の一覧になってしまう。分かりやすく深く、という目的を外す
- 普通の MySQL でしか正しくない説明が、Aurora にも当てはまるように読めてしまう（例: Aurora で redo ログのサイズを調整しようとする）
- 実際には解説のとおりに動かない演習が入っている。間違ったことを覚えることになる
- 既存の学習計画や環境を壊す（`CURRICULUM.md`、3307番ポートの MySQL、`data/` のデータ）
- 業務のデータやクエリ、書籍の本文が入る（このリポジトリの方針に反する）

## 3. 制約

- 手元の Docker Desktop で動くこと。既存の README では Docker に6GB 以上割り当てる前提になっている。このトラックは、任意の CDC 環境（Kafka など）を除いて 2〜3GB に収める。CDC 環境を立てるときは、既存の Spark の環境（`make down`）を止める前提でよい
- MySQL のバージョン
  - 基本は 8.4 LTS。業務の Aurora には v3（8.0 互換）と 8.4 互換版があるので、8.4 を使う。8.0 / Aurora v3 とコマンド名が違うところ（`SHOW MASTER STATUS` → `SHOW BINARY LOG STATUS`、`CHANGE MASTER TO` → `CHANGE REPLICATION SOURCE TO` など）は注記する
  - バージョンをまたぐ章（32）だけ 8.0（最終版の 8.0.46）を使う
- 道具は、Docker Hub、Ubuntu の公式パッケージ、PyPI、Maven Central から取れるものだけを使う。動作確認をする環境（Claude Code のクラウド環境）では、repo.mysql.com と quay.io に届かないため（§8）
- 文書は日本語で、既存の README と同じ文体（「〜する」「〜だ」の平叙。敬語は使わない）
- このリポジトリは公開している。業務のデータ・クエリ・設定値と、書籍の本文は載せない
- 既存のものには触らない。`CURRICULUM.md`、既存の `docker-compose.yml` と `Makefile`、`docker/`、`data/` は変更しない。変更してよいのは、ルートの README の構成表に `mysql-dba/` の行を1行足すことだけ

案1を、本人の希望に合わせて調整して採用した。希望は「全体像を分かりやすく深く解説してほしい」「binlog はデータ連携まで深く」の2つ。調整したのは次の2点。

- 各章は**解説がメイン**。手を動かすのは、解説の内容を確かめるため
- binlog は独立した部にする（第3部）。データ連携（CDC）も独立した部にする（第5部）

## 5. 決まったこと

### 5.1 置き場所と既存との関係

- 全部 `mysql-dba/` に入れる。専用の `docker-compose.yml`（compose のプロジェクト名は `mysql-dba`）と `Makefile` を持たせて、ディレクトリの中だけで完結させる
- データは、既存のシード（`data/seed/*.csv`）とスキーマ（`docker/mysql/init/01_schema.sql`）を読み取り専用でマウントして使う。同じ EC データなので、SQL の問題で慣れたテーブルがそのまま題材になる。将来このディレクトリを別のリポジトリに出すときは、この2つをコピーすればよい
- 大きいテーブルが要る章（バッファプールなど）では、その章の最初に SQL で生成する。生成したデータファイルはコミットしない
- 既存の MySQL（3307番）とポートが重ならないようにする。案として、ソースを 3311、レプリカを 3312、8.0 を 3313 にする。すべて `127.0.0.1` にだけ公開する。既存の compose の `LAB_MYSQL_HOST_PORT` と同じように、環境変数で変えられるようにする
- `mysql-dba/README.md` を入口にする。中身は、目的、進め方、章の一覧とチェックリスト、環境の立ち上げ方、学びのログ、動作確認した環境
- EXPLAIN とインデックス設計は `../rdbms/` に任せる。README からリンクを張る

### 5.2 各章の型

どの章も、次の順で書く。

1. **この章で分かるようになること**（2〜3行）
2. **解説**（章の中心）
   - 仕組み → なぜそうなっているか（何と何のトレードオフか）→ 関係するパラメータ、の順で書く
   - 図を入れる。流れは Mermaid のシーケンス図などで、構造は簡単な ASCII 図や表で描く
   - 解説だけ読んでも分かるように書く。Docker を動かせない場所（スマホで GitHub を見ているときなど）でも読める
3. **手を動かして確かめる**
   - 実験ごとに「予想を書く → 実行する → ここを見る」の順にする
   - 何が起きたかの解説は、予想を書いた後で読めるように `<details>` に入れる
4. **Aurora ではどうなる？**
   - 同じところと、違うところ（置き換わっているもの、設定できないもの、Aurora 独自のもの）を書く
   - 「業務の Aurora で見てみるなら」として、読み取りだけの軽いクエリ、見るべき CloudWatch のメトリクス、待機イベントの名前を載せる。業務の Aurora を触れる立場なら、という書き方にする
   - 本番に負荷をかけるもの（`information_schema.INNODB_BUFFER_PAGE` など）は載せない。載せる場合は「本番では実行しない」と明記する
   - 業務の Aurora で見た値は、このリポジトリ（`notes/` を含む）に書かない。公開しているため。章の中とメモの雛形の両方に注意書きを入れる
   - AWS のドキュメントで確かめた内容だけを書き、出典のリンクを付ける
5. **説明できるか確かめる**
   - 問いを3〜5個置く。答えは載せない（このリポジトリの「答えは自分で書く」に合わせる）
   - 詰まったときに戻る節を示す
6. **この章のキーワード**
   - 同僚との会話で出てくる言葉を、1行の説明付きで並べる

学習者のメモは `mysql-dba/notes/` に書く（章ごとに1ファイル）。解説のファイルには書き込まない。

### 5.3 章立て

全部で21章（うち1章は任意）。1章あたり、解説を読むのに20〜40分、手を動かすのに30〜50分で、合計の目安は20〜25時間。番号は部ごとに10の位を分ける。

#### 第4部 レプリケーション

### 5.4 実行環境

- サービス
  - `src`: MySQL 8.4 のソース。binlog は ON、`binlog_format=ROW`、GTID は ON
  - `rep`: MySQL 8.4 のレプリカ。`super_read_only`
  - `tools`: 道具のコンテナ（後述）
  - 次の2つは compose のプロファイルで、必要な章だけで立てる
    - `old`: MySQL 8.0.46（章32）
    - Kafka + Kafka Connect（章42）
- `src` → `rep` のレプリケーションは、章01から動いている状態にする（全体像の章で、レプリカに届くところまで見せるため）。章30では、学習者が手で設定し直す
  - 注意: ソースとレプリカの両方で初期データを読み込んでから GTID で自動位置合わせをすると、ソース側の読み込みのトランザクションがレプリカで重複してエラーになる。レプリカは空から始めてソースの binlog を全部流すか、clone プラグインで作る
- サーバーのイメージは、公式の `mysql:8.4.x` と `mysql:8.0.46` をそのまま使う。設定は `.cnf` ファイルをマウントして渡す
- 道具のコンテナは Ubuntu 26.04 から作る
  - `mysql-client-core`（mysql、mysqldump、mysqlslap）
  - `mysql-server-core`（mysqlbinlog が入っているのはこちら）。どちらも 8.4 系
  - `sysbench`
  - Python の仮想環境（`pymysql`、`mysql-replication`）
  - 公式の mysql:8.4 イメージには mysqlbinlog と mysqlslap が入っていない（§8）ので、このコンテナが必要になる
- 道具のコンテナには `src` のデータディレクトリを読み取り専用でマウントする。binlog のファイルやデータディレクトリを直接見られるようにするため
- 章42の Kafka Connect は、`apache/kafka` のイメージに、Maven Central から取った Debezium の MySQL コネクタを入れて作る（Debezium 公式のイメージは quay.io にあって、動作確認の環境から取れないため）
- ログインは root を使う（DBA の立場で操作するため）。Aurora のマスターユーザーは SUPER を持たず、一部の操作は `mysql.rds_*` の手続きで代わりにやる、という違いは注記で扱う
- `Makefile` には少なくとも次の操作を用意する
  - 起動、停止、初期化（ボリュームの削除）
  - ソースへのセッション A/B/C。プロンプトで A/B/C を見分けられるようにする
  - レプリカへのセッション
  - 道具のコンテナのシェル
  - 現在の binlog を読みやすく表示する
  - 決まった書き込み負荷をかける
  - 任意のプロファイルの起動
- コミットするファイルは、手元の PC でそのまま動くこと。動作確認の環境でだけ必要なプロキシや証明書の設定は、コミットするファイルに入れない（動作確認のときにだけ外から渡す）

### 5.5 Aurora の扱い

- Docker で再現するのは、普通の MySQL と Aurora で共通の部分（SQL 層、InnoDB のトランザクション・ロック・MVCC、binlog とそのレプリケーション、CDC）
- Aurora で置き換わっている部分（redo の書き先、チェックポイント、doublewrite、クラッシュリカバリ、リーダーの同期）は、「普通の MySQL ではこう → Aurora ではこう置き換えた → だから Aurora ではこのパラメータは意味がない／変えられない」の順で説明する。普通の MySQL での実験は、「Aurora が何を置き換えたのか」を理解するための材料として扱う
- Aurora の事実は、書く時点の AWS のドキュメントで確かめて、出典を付ける。v3（8.0 互換）と 8.4 互換版で違うところは両方書く

### 5.6 文体と書き方

- 既存の README と同じ文体。短い文で、専門用語は最初に出てきたときに一言で説明する
- 英語の用語は、同僚との会話でそのまま出てくる形（binlog、redo、purge、GTID など）を使う。初出で日本語の説明を添える
- 書籍の本文は写さない。MySQL の公式マニュアルや AWS のドキュメントへのリンクは付けてよい

### 5.7 動作確認

- 各章の実験は、固定したバージョンで、解説に書いたとおりに動くことを実際に動かして確かめる。確かめた結果（数字の傾向）が解説と合わない場合は、解説のほうを直す
- `mysql-dba/README.md` の「動作確認した環境」に、確かめたバージョンと日付を書く
- 時間や速さを測る実験は、環境によって数字が変わる。解説には「傾向」（どちらが速いか、およそ何倍か）だけを書いて、具体的な数字は学習者が自分の環境で測るものとする。Docker Desktop の fsync の挙動で差が小さく出ることがある、という注意も書く

## 7. 作るときに判断した点（作る人の判断として明記するもの）

- データは既存のシードを使う（§5.1）
- ルートの README には構成表に1行足すだけにして、`CURRICULUM.md` には手を入れない
- 解説の後の「何が起きたか」は `<details>` に入れて載せる。章末の「説明できるか確かめる」の答えは載せない。前者は解説の一部、後者は自分で答える練習、という区別
- 学習者のメモは解説のファイルとは別にする
- CDC の比較の対象は、Debezium、AWS DMS、Aurora の zero-ETL（Redshift 向け）にする。業務で別のツールを使っていれば、それを足す
- 「業務の Aurora で見てみるなら」の節は入れる。業務の Aurora を触れない場合は飛ばせばよいように書く
- 章50の早見表は、自分で埋める雛形だけを置く（このリポジトリの「答えは自分で書く」に合わせる）。各パラメータの説明は各章の解説にある

## 8. 前提として調べたこと（2026-11-20 時点）

- MySQL 8.0 は2026年4月でサポートが終わった（最終版は 8.0.46）。LTS は 8.4 と 9.7（2026年4月21日 GA）。次の Innovation リリースからは、バージョン番号が年.月の形（26.7）になった
- Aurora MySQL は、v3（MySQL 8.0 互換）と、8.4 互換版（最初の版は 8.4.7、2026年5月21日）がある。8.4.8 で、複数のソースからの binlog レプリケーションに対応した
- Aurora MySQL では binlog がデフォルトで OFF。Blue/Green デプロイは、ブルーからグリーンへの binlog レプリケーションを使うので、binlog を有効にしたクラスターのパラメータグループが必要になる。形式は ROW が推奨されている
- Aurora MySQL の履歴リストの長さはクラスター単位で、リーダーの長いトランザクションでも伸びる
- 公式の `mysql:8.4` イメージ（8.4.13）には、mysql、mysqldump、mysqladmin、mysqlsh は入っているが、mysqlbinlog、mysqlslap、Python は入っていない。`mysql:8.0` も同じ（8.0.46）
- Ubuntu 26.04 の公式パッケージで MySQL 8.4.13 のクライアントが入る。mysql と mysqldump と mysqlslap は `mysql-client-core`、mysqlbinlog は `mysql-server-core`。sysbench 1.0.20、Python 3.14 も入る
- PyPI の `mysql-replication` 1.0.17 は、8.4 の `SHOW BINARY LOG STATUS` に対応している（使えないときは `SHOW MASTER STATUS` に切り替わる）
- Debezium の MySQL コネクタは Maven Central にある（3.7.1.Final が最新の安定版）。Kafka は `apache/kafka:4.1.1` が Docker Hub にある
- 動作確認をする環境から届くのは、Docker Hub、Ubuntu の公式パッケージ、PyPI、Maven Central。repo.mysql.com と quay.io には届かない
